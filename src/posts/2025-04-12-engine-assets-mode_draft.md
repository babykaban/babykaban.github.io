### How does game fetches assets?
The asset fetching/loading was taken from Handmade Hero series, the general idea is that you have all assets in one file, that can be accsesed by and ID and data offset, to make it esier to find each asset has its Type and tags which are just 'enum' numbers. The file goes like this, first you have a header that contains MagicValue, Version, TagCount, TypeCount, AssetCount, after counts three data offsets follow, first is the offset to tag array next offset to type array and the last offset to asset array.

Asset it self contains offset to its data, first index into tag array and one past last index, to make it esier to work with the tags for a particular asset are continius meaning that first index for example 55 is the first tag of the asset and one past last index of the asset lets say 60 is the next asset's first index every tag in between 55 and 60 are tags of the asset. After tag indecies the union of structs follows which are specific to an asset, that allows to calculate how many bytes to read to load all of the data for the asset and/or some configurations, for bitmap for example it would be width and height to calculate how many bytes to read and align offset.

But how do we know what asset we are loading? Well we don't really know, all we know is what type of asset we want to load and what tags it has basically it is intuitive if we say that we want an asset by type Asset_Tree, one whould assume that it is a bitmap or spritesheet, but other might think it is a sound, it that case we also specifies tags for this asset like Tree_Tall or Tree_WithLeaves or Tree_Old, now we know that it most likely to be bitmap or spritesheet, and not sound. Asset_type is a struct that contains three values first is a TypeID, the first asset index and one past last asset index. It works the same way as tags in assets itself.

That was a lot of explenation I will give an example how it works. Lets create an asset:
- Asset type will be Bitmap, vissualy it is a tall tree with leaves
- Asset tags will be Tag_TreeType with a value of Tree_Leveas, Tag_Size with value of Tree_Tall
- And we store data for this asset by loading a bitmap and specifing first it configurations for the asset, and then storing its content at current data offset.

Now we have one asset in our asset file. Lets say we want to load it in the game and render it. First we do LoadAsset load asset takes AssetHeaderType which is a consept for the loader it self to know what we are loading, bitmap, sound, font, spritesheet etc. Also we provide LoadAsset with asset ID. But how do we get the ID. To get the asset ID we use one of the GetBestMatch function, this function takes Asset_Type, and tags and values to those tags to search though all assets in specified type array and compare the tags to find the best match. So we first call the GetBestMatchBitmap with Asset_Type being Asset_Tree, and asset tags stated above. As a result we get basically an index into the array of assets to load it. Then we call LoadAsset function, we want to load a Bitmap which by an ID that we just got, and that is it we loaded our asset now we can use it in the game.

### What I have changed?

There was one issue that I faced that I can't even explain right know because it was a long while ago, but issue wast that if I write asset that has data which is indecies to the other assets in the asset file and I won't write them in order the stored indecies will not work, for example if I write spritesheet which is asset that I defined, that contains an array of indecies to its sprites that are in the asset file too, then I add a bitmap, and then another spritesheet the indecies will be off, because the requirement is that all asset types are continius. lets say I add spritesheet, first I add its sprites with indecies 1, 2, 3 and 4, and a spritesheet itself with index 5, then I add another spritesheet, sprites go 6, 7, 8, 9, and spritesheet 10. Now the first spritesheet will work fine but the next won't. Because the type array for sprites is screwed up no it goes from 1 to 9 including the first spritesheet but it was suppost to go from 1 to 8 and then the spritesheet had to be added to remain the order.

That is a bad explanation of the problem but that is a description that I remember straggling with, bassically to make this system work you need to remain an order of assets of the same type. If you manage to do that everything works just fine.

So to fix this I decided to first integrate the asset building into the engine it self because before it was an external program that builds it and all of the assets to write were hardcoded in order. The fix was kind of simple, each time I add a new asset I need to check if its type array is first, or goes before or after the other types, if it is first I need to advance all ids of the assets below by one if it is in between the types then I need to advance all ids of the assets that go after it and if it is last type then I don't need to do anything.

Then I decided to create a file format that will be used to store assets raw data, their type, tags, and data source. So for bitmap it will be its type, tags, source file name, and alignment. This file also has a header that contains basic info size of the largest stored asset, stored asset count, version, and magic value. Why the size of the largest asset? All of the stored assets are of the same size because they have common info like type and then the union and because I use union the size of the structure will be the size of the largest element in the union. It simplifies reading of the file.

After that I added the UI to make it convinient to add new assets or remove old ones. So the algorithm goes like this, first I start the Assets edit mode, that allows to add new assets to stored asset file and ultimatly update its version because it is different from previous one, then I may choose to write the assets to the asset file, it creates completely new asset file that contains all of stored assets. Even though Casey added support for multiple asset files to be loaded at the same time I decided that it will be simpler if I just write everything correctly into one file and if I need new assets I just rebuild an asset file because the functionality I already added so its a press of one button.
